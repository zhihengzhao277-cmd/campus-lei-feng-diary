# 第一部分：Gate 2 方法、对象集合与建模原则

## 1. Gate 2 的目标

Gate 1 回答的是：

> **“系统需要做什么？”**

Gate 2 要回答的是：

> **“系统中存在哪些业务对象？这些对象分别负责什么？对象之间最终应该如何建立业务关系？”**

当前 Gate 2 的重点不是立即写 C++ 类，而是先建立稳定的业务模型。

本阶段主要工作包括：

1. 识别候选领域对象；
2. 区分真正的业务对象、配置对象、关系对象和派生结果；
3. 明确每个对象的核心职责；
4. 避免为了满足“类数量要求”而机械拆类；
5. 为后续对象关系、组合/聚合、继承、多态和最终类设计提供依据；
6. 保证领域模型能够与 Gate 1 已冻结需求一一对应；
7. 保证每个对象存在清晰的业务意义和可解释性。

---

## 2. 当前建模原则

## 2.1 不把“所有名词”都直接做成类

一个业务名词是否值得成为独立领域对象，需要判断它是否具有：

- 独立数据；
- 独立状态；
- 独立生命周期；
- 独立业务职责；
- 与其他对象稳定的协作关系。

不能仅仅因为某个概念“在需求中出现过”，就直接把它设计成类。

## 2.2 不为了凑类数量进行机械拆分

课程要求类数量不少于 5 个，但本项目不以“凑够 5 个类”作为设计目标。

当前系统本身已经自然产生多个具有独立业务职责的对象，因此后续应优先保证：

- 职责合理；
- 边界清晰；
- 协作自然；
- 便于解释；
- 便于维护。

而不是人为制造没有业务意义的类。

## 2.3 暂不冻结最终 C++ 类结构

Gate 2 当前讨论的是领域对象。

例如：

- 学生是一个领域角色；
- 管理员是一个领域角色。

但当前并不直接决定最终一定采用：

```text
User
├── Student
└── Administrator
```

这种继承结构。

是否建立共同基类、怎样体现继承和多态，将进入 Gate 3 架构审计后结合课程评分要求、实际业务逻辑和代码可解释性进一步决定。

因此：

> **领域对象 ≠ 最终 C++ 类结构。**

---

## 3. Gate 2.1：候选领域对象识别

经过当前讨论，候选对象已经收敛为三类。

## 3.1 核心业务对象

当前确定的核心业务对象包括：

1. 学生；
2. 管理员；
3. 志愿记录；
4. 志愿类别；
5. 日记墙内容。

这些对象直接参与系统主要业务流程，并具有相对独立的业务职责。

## 3.2 配置 / 支撑对象

当前确定的配置或支撑对象包括：

1. 专项徽章规则；
2. 学期；
3. 操作日志。

这些对象虽然不是“学生提交志愿记录”主流程的中心，但具有独立数据、状态或管理职责，因此仍然需要独立建模。

## 3.3 关系对象

当前明确存在的关系对象：

1. 点赞关系。

点赞关系不是普通的“点赞数量”。

它表达的是：

> **某一个具体学生，对某一条具体日记墙内容，是否建立过点赞关系。**

为了实现：

> **一个学生对同一条日记墙内容最多点赞一次**

仅保存 `likeCount` 是不够的。

系统还必须知道：

- 谁点了赞；
- 点了哪一条；
- 这条关系是否存在。

因此点赞关系具有明确的独立建模价值。

---

## 4. 当前明确不作为核心领域实体的概念

以下概念当前不单独作为核心领域对象：

- 月度积分；
- 学期积分；
- 总积分；
- 排行榜；
- 当前排名；
- 排行榜称号；
- 当前专项徽章等级；
- 点赞数量。

主要原因是这些概念本质上属于：

> **由当前有效业务数据和规则计算得到的派生结果。**

## 4.1 为什么积分不直接作为独立核心对象

月度积分、学期积分和总积分都来自当前有效志愿记录。

例如：

```text
总积分
=
当前全部有效且已经完成结算的志愿记录积分之和
```

因此“总积分”不应该成为一个可以随意单独修改的独立业务事实。

如果同时保存：

- 志愿记录中的结算积分；
- 学生对象中的总积分；

就可能产生：

```text
记录被删除
↓
记录数据发生变化
↓
但学生总积分字段没有同步更新
↓
出现数据不一致
```

所以当前领域模型坚持：

> **积分汇总属于计算结果。**

## 4.2 为什么排行榜不直接作为核心对象

排行榜本质上是根据某个统计范围：

1. 汇总学生有效积分；
2. 汇总有效服务时长；
3. 汇总有效记录数量；
4. 按既定规则排序；

形成的展示结果。

当前排序规则已经在 Gate 1 冻结为：

1. 积分降序；
2. 有效服务总时长降序；
3. 有效志愿记录数降序；
4. 学号升序。

因此排行榜当前更适合作为：

> **统计与排序结果**

而不是一个拥有独立业务生命周期的核心实体。

## 4.3 为什么排行榜称号不直接作为独立对象

月度、学期、总榜的排行称号均根据当前排名动态决定。

例如：

```text
当前月度第 1 名
→ 月度雷锋之星·金
```

当排行榜发生变化时，称号也随之变化。

因此当前排行榜称号属于：

> **当前排行榜状态的派生结果**

而不是永久独立保存的业务实体。

## 4.4 为什么“当前徽章等级”不直接作为独立对象

专项徽章等级由：

```text
学生当前某类别有效服务时长
+
当前专项徽章规则
```

共同决定。

例如：

```text
环保实践有效时长 = 35 小时
银级门槛 = 30 小时
→ 当前环保卫士等级 = 银
```

如果管理员修改门槛，或者历史有效志愿记录被删除，学生当前徽章等级可能重新下降。

因此：

> **当前徽章等级属于动态计算状态。**

而真正需要独立建模的是：

> **专项徽章规则。**

## 6. Gate 2.2：对象职责定义总原则

对象职责定义采用：

> **“这个对象代表什么 + 它应该负责什么 + 它不应该负责什么”**

的方式进行。

当前暂不直接写最终：

- C++ 方法；
- getter/setter；
- Qt 槽函数；
- 文件读写函数；
- 类继承体系。

## 20. 当前已冻结的 Gate 2 设计结论

截至当前，已经确认：

1. 学生是独立核心领域对象。
2. 管理员是独立核心领域对象。
3. 学生不仅是身份主体，同时是志愿记录者 / 志愿申请者。
4. 管理员不仅是身份主体，同时是志愿审核者 / 系统治理者。
5. 学生必须保留“维护学生身份与账号状态，并作为志愿记录、点赞等学生行为归属主体”这一层职责。
6. 管理员必须保留“维护管理员身份与账号状态，并作为审核、治理和配置操作执行主体”这一层职责。
7. 志愿记录是整个系统最核心的业务载体之一。
8. 志愿类别不是简单字符串，而是独立规则对象。
9. 日记墙内容正式作为独立领域对象。
10. 日记墙内容定位参考 QQ 空间 / 小红书式信息流。
11. 日记墙内容必须依附于真实、当前存在且审核通过的志愿记录。
12. 日记墙内容允许学生独立编辑展示标题和展示文案。
13. 日记墙中的事实字段仍然来自审核通过的原志愿记录。
14. 专项徽章规则作为独立配置对象。
15. 学生当前专项徽章等级不作为独立核心实体。
16. 学期作为独立时间配置对象。
17. 操作日志作为独立审计对象。
18. 点赞关系作为独立关系对象。
19. 月度积分、学期积分、总积分属于派生统计结果。
20. 排行榜属于派生排序结果。
21. 排行榜称号属于当前排行榜派生状态。
22. 当前专项徽章等级属于当前有效数据和徽章规则共同计算得到的派生状态。

# 第二部分：角色与账号主体——对应 Gate 1 角色/权限域

## 7. 学生对象

## 7.1 学生对象的业务定位

当前正式定义：

> **学生既是系统中的学生身份主体，也是志愿业务的发起者 / 志愿申请者。**

学生不能只被理解为一组静态个人信息。

学生是整个志愿业务流程的主要发起方。

## 7.2 学生对象的第一层职责：身份职责

学生需要：

- 维护自己的学生身份；
- 维护自身账号状态；
- 保存与学生本身相关的基础资料；
- 作为学生行为的归属主体。

至少包括：

- 学号；
- 姓名；
- 班级；
- 专业；
- 联系方式；
- 账号状态。

## 7.3 学生作为行为归属主体

系统中很多业务行为必须能够明确回答：

> **“是谁做的？”**

因此学生同时作为：

- 志愿记录的归属主体；
- 日记墙内容发布主体；
- 点赞行为主体。

也就是说：

```text
一条志愿记录
→ 必须属于某个学生

一条日记墙内容
→ 必须存在发布学生

一次点赞
→ 必须知道是哪名学生执行
```

## 7.4 学生对象的第二层职责：业务职责

学生同时是：

> **志愿记录者 / 志愿申请者。**

学生实际承担的志愿业务包括：

- 创建自己的志愿记录；
- 提交志愿记录；
- 查看自己的记录；
- 在管理员审核前修改自己的待审核记录；
- 在管理员审核前撤回自己的待审核记录；
- 查看管理员审核结果；
- 查看管理员审核意见；
- 对驳回记录进行修改；
- 对驳回记录重新提交；
- 基于自己的当前存在的已通过志愿记录申请日记墙展示；
- 参与日记墙点赞；
- 取消自己的点赞。

## 7.5 学生对象当前核心职责总结

学生当前正式职责可以概括为：

> **维护学生身份与账号状态，并作为志愿记录、日记墙发布、点赞等学生行为的归属主体；同时作为志愿服务参与者和志愿申请者，负责发起和管理自己的志愿记录及相关公开互动行为。**

可以进一步拆成：

```text
学生
├── 身份职责
│   ├── 学生身份
│   ├── 账号状态
│   └── 行为归属
│
└── 业务职责
    ├── 志愿申请
    ├── 志愿记录管理
    ├── 日记墙展示申请
    └── 点赞互动
```

## 7.6 学生对象明确不负责的内容

当前不将以下职责放入学生对象：

- 审核志愿记录；
- 修改积分规则；
- 设置专项徽章门槛；
- 配置学期；
- 管理全局用户；
- 删除他人违规记录；
- 计算整个系统排行榜；
- 管理系统操作日志。

这些职责不属于学生这一领域角色。

---

## 8. 管理员对象

## 8.1 管理员对象的业务定位

当前正式定义：

> **管理员既是系统中的管理身份主体，也是志愿审核者和系统治理者。**

管理员不是单纯的“账号”。

也不是无约束的“超级 CRUD 用户”。

管理员的核心定位仍遵循 Gate 1：

> **审核 + 治理 + 配置**

## 8.2 管理员对象的第一层职责：身份职责

管理员需要：

- 维护管理员身份；
- 维护管理员账号状态；
- 作为系统管理行为的执行主体。

至少具有：

- 管理员账号；
- 姓名；
- 账号状态。

## 8.3 管理员作为管理行为执行主体

系统中的关键管理操作必须可以明确追踪：

> **“是哪一个管理员执行的？”**

因此管理员必须作为：

- 志愿审核行为的执行主体；
- 记录治理行为的执行主体；
- 用户管理行为的执行主体；
- 积分规则配置行为的执行主体；
- 徽章规则配置行为的执行主体；
- 学期配置行为的执行主体；
- 日记墙审核 / 下架行为的执行主体；
- 数据导出行为的执行主体。

这也是操作日志能够实现责任追溯的重要基础。

## 8.4 管理员对象的第二层职责：志愿审核职责

管理员负责：

- 查看学生待审核志愿记录；
- 审核志愿记录；
- 审核通过；
- 审核驳回；
- 填写审核意见；
- 确认学生申报类别；
- 必要时修正最终类别；
- 确认学生申报时长；
- 必要时修正最终时长；
- 对异常已通过记录进行治理；
- 对违规或错误记录进行必要更正或删除。

管理员是志愿记录从“申请数据”变成“有效结算数据”的核心审核主体。

## 8.5 管理员对象的第三层职责：系统治理与维护

管理员负责系统层面的治理和维护，包括：

- 学生账号管理；
- 志愿类别管理；
- 当前积分规则管理；
- 专项徽章规则管理；
- 学期管理；
- 日记墙内容治理；
- 日记墙展示申请审核；
- 不适合继续公开的日记墙内容下架；
- 查看系统操作日志；
- 执行数据导出；
- 查看全局统计。

## 8.6 管理员对象当前核心职责总结

管理员当前正式职责可以概括为：

> **维护管理员身份和账号状态，并作为审核、治理和配置操作的执行主体；同时负责志愿记录审核，以及系统用户、业务规则、学期配置、专项徽章规则和日记墙公开内容的治理与维护。**

可以进一步拆成：

```text
管理员
├── 身份职责
│   ├── 管理员身份
│   ├── 账号状态
│   └── 管理行为归属
│
└── 业务职责
    ├── 志愿审核
    ├── 异常记录治理
    ├── 用户管理
    ├── 积分规则管理
    ├── 徽章规则管理
    ├── 学期管理
    ├── 日记墙治理
    ├── 日志审计
    └── 数据导出
```

## 8.7 管理员对象职责边界说明

虽然管理员能发起很多管理行为，但后续设计时应避免：

> **把整个系统所有业务逻辑全部塞入 Administrator 一个类。**

当前领域层面可以说：

> 管理员负责这些业务。

但进入 Gate 3 后需要进一步判断：

- 哪些属于管理员对象自身行为；
- 哪些应由独立业务服务 / 管理对象负责；
- 哪些属于规则对象自身职责；
- 哪些属于数据仓储或持久化模块职责。

目的在于避免形成：

> **“万能管理员类 / 上帝类”**

---

## 19. 学生和管理员的双层职责模型

当前一个非常重要的设计结论是：

> **学生和管理员不能只看“业务动作”，也不能只看“身份数据”。**

两者都应采用：

```text
身份职责
+
业务职责
```

的双层理解。

学生：

```text
身份层：
学生身份 + 账号状态 + 行为归属

业务层：
志愿申请 + 志愿记录管理 + 日记墙申请 + 点赞
```

管理员：

```text
身份层：
管理员身份 + 账号状态 + 管理行为归属

业务层：
审核 + 治理 + 配置 + 系统维护
```

这一结论已经确认，应在后续领域建模中保持。

---

## 23. 学生与志愿记录的关系

当前确定：

> **一个学生可以拥有多条志愿记录，一条志愿记录只能属于一个学生。**

业务表示：

```text
Student 1 ---- N VolunteerRecord
```

学生是志愿记录的提交者、志愿申请的发起者和业务归属主体。

志愿记录必须能够回答：

> **“这条记录属于哪一名学生？”**

学生对象不需要复制保存每一条志愿记录的完整业务数据。志愿记录自身必须保存所属学生关联。

最终 C++ 是否在 `Student` 内部直接保存记录容器，当前暂不冻结，留待 Gate 3 决定。

---

## 24. 管理员与志愿记录的关系

管理员不是志愿记录的拥有者。

管理员与志愿记录之间属于：

> **审核 / 治理关联**

业务表示：

```text
Administrator ---- reviews / governs ---- VolunteerRecord
```

一名管理员可以审核和治理多条志愿记录。

一条志愿记录的审核结果必须能够追溯：

> **该次审核由哪一名管理员执行。**

因此当前确定需要保留：

> **审核执行管理员**

这一业务关系。

这样可以支持：

- 追溯谁审核通过；
- 追溯谁执行驳回；
- 与操作日志相互对应；
- 异常争议责任追溯。

具体最终保存管理员 ID、对象引用还是其他表示方式，进入 Gate 3 再定。

---

## 25. 管理员与学生的关系

管理员与学生之间存在：

> **用户管理关联**

业务表示：

```text
Administrator ---- manages ---- Student
```

管理员可以：

- 创建学生账号；
- 禁用学生账号；
- 恢复学生账号；
- 重置密码；
- 管理允许由管理员维护的学生身份信息。

但是管理员与学生之间不存在生命周期拥有关系。

某一名管理员不存在或被移除，不意味着学生对象随之消失。

因此当前不能把管理员与学生理解成组合关系。

---

## 26. 学生、管理员与志愿记录的核心主链

```text
学生
  │
  │ 提交 / 归属
  ▼
志愿记录
  ▲
  │ 审核 / 治理
  │
管理员
```

核心区别：

> **学生是志愿记录的业务归属主体。**

> **管理员是志愿记录的审核与治理主体。**

# 第三部分：志愿记录与积分结算——对应 Gate 1 志愿主业务域

## 9. 志愿记录对象

## 9.1 志愿记录的业务定位

志愿记录是当前系统最核心的业务对象之一。

它承载：

> **学生申报的志愿事实 + 管理员审核过程 + 最终结算结果。**

它是连接：

```text
学生
↓
志愿申请
↓
管理员审核
↓
积分结算
↓
排行榜 / 徽章 / 日记墙资格
```

的中心业务载体。

## 9.2 志愿记录需要承载的主要事实

当前至少包括：

- 记录编号；
- 所属学生；
- 服务日期；
- 申报类别；
- 最终确认类别；
- 申报时长；
- 最终确认时长；
- 地点；
- 证明人；
- 简述；
- 审核状态；
- 审核意见；
- 结算时积分系数；
- 最终结算积分。

## 9.3 志愿记录拥有独立业务状态

当前志愿记录至少存在：

- 待审核；
- 已通过；
- 已驳回；
- 已撤回。

因此它并不是普通静态数据结构，而具有明确业务生命周期。

## 9.4 志愿记录的生命周期职责

志愿记录需要能够表达：

```text
学生创建
↓
提交
↓
待审核
↓
├── 学生修改
├── 学生撤回
└── 管理员审核
      ↓
   ├── 通过
   └── 驳回
          ↓
       学生修改
          ↓
       重新提交
```

审核通过后还可能因为异常治理发生：

- 强制更正；
- 管理员物理删除。

删除不是志愿记录的一种业务状态。志愿记录一旦被物理删除，就不再作为 `VolunteerRecord` 对象存在；删除原因、执行管理员和删除时间由操作日志负责留痕。

## 9.5 志愿记录当前核心职责总结

当前正式定义：

> **封装一条志愿服务记录的完整事实、申报信息、审核状态和最终结算结果，并维护这条记录从学生提交、管理员审核到最终生效、撤回、驳回或被管理员删除前的业务生命周期。**

## 9.6 志愿记录明确不负责的内容

当前不让志愿记录直接负责：

- 整个系统排行榜排序；
- 所有学生总积分统计；
- 学期配置管理；
- 专项徽章门槛配置；
- 日记墙公开文案编辑；
- 用户账号管理。

志愿记录只负责：

> **“这一条志愿业务自身是什么、经历了什么审核、最终如何结算。”**

---

## 10. 志愿类别对象

## 10.1 志愿类别不是简单字符串

当前志愿类别不能仅理解成：

```text
"环保实践"
```

因为它同时拥有：

- 类别名称；
- 当前积分系数；
- 启用状态。

并且管理员可以：

- 查看；
- 修改系数；
- 新增；
- 停用。

因此志愿类别具有独立配置生命周期。

## 10.2 志愿类别的业务职责

志愿类别主要负责：

- 定义一种志愿服务类型；
- 保存当前积分系数；
- 保存是否启用；
- 为学生申报提供类别选项；
- 为管理员最终确认类别提供依据；
- 为新审核通过的志愿记录提供当前结算规则。

## 10.3 志愿类别当前核心职责总结

正式定义：

> **定义一种志愿服务类型及其当前积分规则，为志愿记录的分类和积分结算提供依据。**

## 10.4 志愿类别明确不负责的内容

志愿类别不负责：

- 汇总某学生总积分；
- 计算排行榜；
- 判断学生当前徽章等级；
- 审核志愿记录真实性；
- 保存历史所有记录的当前实时分数。

特别需要注意：

历史已经结算的志愿记录采用：

> **审核结算时冻结的积分系数和最终积分。**

因此志愿类别中的当前系数只影响后续新结算业务，不追溯修改历史已经结算记录。

---

## 27. 志愿记录与志愿类别的关系

一条志愿记录分别涉及：

1. 学生申报类别；
2. 管理员最终确认类别。

因此业务关系可以理解为：

```text
VolunteerRecord
├── appliedCategory → VolunteerCategory
└── finalCategory   → VolunteerCategory
```

从类别角度看：

> **一种志愿类别可以被多条志愿记录使用。**

业务表示：

```text
VolunteerCategory 1 ---- N VolunteerRecord
```

申报类别与最终类别可以相同，也可以在管理员审核后不同。

虽然志愿记录关联最终类别，但历史已经结算的志愿记录不能根据当前 `VolunteerCategory` 的最新积分系数重新计算。

因此审核通过时，志愿记录还必须独立固化：

- 结算时实际使用的积分系数；
- 最终结算积分。

这说明：

> **志愿记录与志愿类别之间是业务关联关系，而历史结算结果属于志愿记录自身必须保存的历史事实。**

---

## 29. 创建日记墙内容的硬前置条件

正式冻结：

> **只有当前存在且审核通过的志愿记录，才允许学生申请生成日记墙内容。**

状态约束为：

```text
待审核  → 不允许生成日记墙内容
已驳回  → 不允许生成日记墙内容
已撤回  → 不允许生成日记墙内容
已通过  → 可以申请生成日记墙内容
```

志愿记录只保留四种业务状态：

- 待审核；
- 已通过；
- 已驳回；
- 已撤回。

不额外设置：

- `Deleted`；
- `Invalid`；
- `isDeleted`；
- `isValid`。

如果管理员执行删除，则该志愿记录被物理删除，不再作为业务对象存在。

---

## 30. 原志愿记录被删除后的日记墙联动

如果一条已经生成日记墙内容的志愿记录后来因为异常、违规或管理员治理被正式删除，则：

> **关联的日记墙内容同步删除。**

与该日记墙内容关联的点赞关系也同步清理。

原因是：

- 日记墙内容必须来源于真实、审核通过的志愿记录；
- 原志愿记录一旦被物理删除，帖子便失去业务来源；
- 保留一个引用不存在志愿记录的日记墙帖子会破坏数据完整性。

删除志愿记录后的联动原则：

```text
VolunteerRecord
    ↓ 物理删除
DiaryPost
    ↓ 同步删除
LikeRelation
    ↓ 同步清理

积分 / 排行榜 / 排行称号 / 专项徽章
    ↓
重新计算

OperationLog
    ↓
保留删除行为审计信息
```

操作日志负责记录被删除记录、删除原因、执行管理员和操作时间，因此不需要为了审计而在 `VolunteerRecord` 中保留“已删除”状态。

---

# 第四部分：专项徽章、学期与派生荣誉——对应 Gate 1 荣誉/统计域

## 12. 专项徽章规则对象

## 12.1 业务定位

专项徽章规则属于：

> **配置型领域对象。**

它定义的不是：

> “学生现在有什么徽章”

而是：

> “某一种专项徽章按照什么条件达到铜 / 银 / 金等级”。

## 12.2 专项徽章规则至少需要表达的信息

当前至少包括：

- 徽章名称；
- 对应志愿类别；
- 铜级门槛；
- 银级门槛；
- 金级门槛；
- 是否启用。

## 12.3 专项徽章规则的业务职责

它负责：

- 定义专项徽章名称；
- 绑定对应志愿类别；
- 定义铜级门槛；
- 定义银级门槛；
- 定义金级门槛；
- 定义是否启用；
- 为当前学生徽章等级判定提供规则依据。

## 12.4 专项徽章规则当前核心职责总结

正式定义：

> **定义某一志愿类别对应的专项徽章及铜、银、金三级门槛，为学生当前徽章等级的动态判定提供规则依据。**

## 12.5 专项徽章规则与学生当前徽章等级的区别

必须明确：

```text
专项徽章规则
≠
学生当前徽章等级
```

专项徽章规则是：

> 独立配置对象。

学生当前徽章等级是：

> 根据学生当前有效专项服务时长和当前徽章规则动态计算得到的结果。

---

## 13. 学期对象

## 13.1 业务定位

学期属于：

> **时间配置对象。**

它用于定义当前统计周期。

## 13.2 学期对象至少需要表达的信息

当前至少包括：

- 学期名称；
- 开始日期；
- 结束日期；
- 是否当前学期。

系统允许存在多个学期配置，但同一时间只存在一个当前学期。

## 13.3 学期对象的业务职责

学期主要负责：

- 定义一个学期名称；
- 定义学期起始日期；
- 定义学期结束日期；
- 表达是否为当前学期；
- 为学期积分统计提供时间范围；
- 为学期排行榜提供时间范围；
- 为学期排行称号提供当前统计上下文。

## 13.4 学期对象当前核心职责总结

正式定义：

> **定义一个学期的有效时间范围及当前学期状态，为学期范围内的积分统计和排行榜计算提供时间边界。**

## 13.5 学期对象明确不负责的内容

学期对象不负责：

- 直接计算学生积分；
- 自己完成排行榜排序；
- 修改志愿记录；
- 审核志愿记录；
- 管理徽章。

它只提供：

> **时间边界。**

---

## 36. 志愿类别与专项徽章规则的关系

当前确定：

> **一个专项徽章规则必须对应一个志愿类别。**

同时：

> **一个志愿类别当前最多对应一套专项徽章规则。**

业务表示：

```text
VolunteerCategory 1 ---- 0..1 BadgeRule
```

当前每个类别采用一套完整的铜 / 银 / 金成长体系，因此同一个志愿类别没有必要并存多套专项徽章规则。

如果某类别暂时不设置专项徽章，则允许 0 个 `BadgeRule`。

---

## 37. 学生与专项徽章规则的关系

学生与专项徽章规则：

> **不建立“永久拥有”关系。**

学生当前徽章等级来自：

```text
学生
↓
统计某志愿类别当前有效服务时长
↓
查找该类别对应 BadgeRule
↓
根据铜 / 银 / 金门槛判断
↓
当前徽章等级
```

所以学生当前徽章等级仍然是派生结果。

---

## 38. 学期与志愿记录的关系

学期不拥有志愿记录。

志愿记录拥有自己的服务发生日期，学期只提供：

- 开始日期；
- 结束日期。

系统统计时依据：

```text
semester.startDate
<= record.serviceDate
<= semester.endDate
```

判断记录是否进入某学期统计范围。

因此学期与志愿记录之间更准确地属于：

> **统计依赖 / 时间范围筛选关系。**

业务表示：

```text
Semester
---- provides date range for ----
VolunteerRecord statistics
```

这样管理员切换当前学期时：

- 不需要移动志愿记录；
- 不需要复制志愿记录；
- 不需要修改志愿记录所属关系；
- 只改变当前统计时间范围。

---

# 第五部分：日记墙与点赞——对应 Gate 1 公开互动域

## 5. 日记墙对象定位的重大调整

Gate 2 初始讨论中，对日记墙进行了进一步明确。

当前正式确定：

> **日记墙内容是独立领域对象，不等同于志愿记录的简单展示状态。**

这一调整已经同步进入 Gate 1 v1.3。

## 5.1 日记墙产品定位

日记墙计划做成类似：

- QQ 空间；
- 小红书；

的信息流式公开展示区域。

其重点不只是“把志愿记录表格展示出来”，而是形成具有一定内容表达和互动属性的公开帖子。

日记墙内容因此拥有自己的：

- 内容编号；
- 发布学生；
- 关联志愿记录；
- 展示标题；
- 展示文案；
- 展示状态；
- 正式公开时间；
- 点赞关系。

## 5.2 日记墙与志愿记录的职责边界

当前明确：

### 志愿记录负责

- 真实志愿事实；
- 服务日期；
- 服务类别；
- 服务时长；
- 服务地点；
- 证明人；
- 业务审核；
- 积分结算；
- 是否属于有效业务记录。

### 日记墙内容负责

- 对外公开表达；
- 展示标题；
- 展示文案；
- 展示状态；
- 正式公开时间；
- 点赞互动；
- 公开传播。

因此：

> **志愿记录负责“事实真实性与结算”，日记墙内容负责“公开传播与表达”。**

## 5.3 日记墙内容必须来源于真实志愿记录

虽然日记墙是独立对象，但它不能完全独立于志愿业务产生。

当前冻结：

> **每一条日记墙内容必须关联一条真实、有效、已经审核通过的志愿记录。**

学生不能脱离志愿记录直接发布一个无业务来源的帖子。

## 5.4 日记墙允许独立编辑的内容

学生申请进入日记墙时，可以在原志愿记录基础上进行二次公开表达。

允许独立填写：

- 展示标题；
- 展示文案。

这样可以避免日记墙变成单纯复制原始记录简述的表格页面。

## 5.5 日记墙不允许学生修改的事实字段

以下公开事实仍然必须从审核通过后的志愿记录中读取：

- 学生姓名；
- 志愿类别；
- 服务日期；
- 服务时长；
- 地点；
- 本条记录积分。

学生不能为了公开展示效果自行改变这些业务事实。

---

## 11. 日记墙内容对象

## 11.1 业务定位

当前正式确定：

> **日记墙内容是独立的公开内容对象。**

它不是 `VolunteerRecord` 上的一个简单 Boolean 展示字段。

## 11.2 日记墙内容的独立数据

当前至少具有：

- 内容编号；
- 关联志愿记录；
- 发布学生；
- 展示标题；
- 展示文案；
- 展示状态；
- 正式公开时间；
- 点赞关系。

点赞数量由当前关联的 `LikeRelation` 数量动态统计，不作为 `DiaryPost` 的独立持久事实。

## 11.3 日记墙内容的独立生命周期

日记墙内容拥有：

- 创建展示申请；
- 待展示审核；
- 展示审核通过；
- 已展示；
- 已下架；

等自己的状态变化。

该生命周期与原志愿记录生命周期不同。

例如：

```text
志愿记录 = 已通过且有效
日记墙内容 = 已下架
```

是完全允许的。

此时：

- 志愿记录仍然有效；
- 积分仍然有效；
- 排行榜仍然有效；
- 徽章仍然有效；
- 只是公开帖子不再展示。

## 11.4 日记墙内容的业务职责

日记墙内容负责：

- 关联真实、当前存在且审核通过的志愿记录；
- 关联发布学生；
- 保存公开展示标题；
- 保存公开展示文案；
- 维护公开展示状态；
- 维护正式公开时间；
- 承载点赞互动关系；
- 为信息流页面提供公开内容数据。

## 11.5 日记墙内容当前核心职责总结

正式定义：

> **负责承载基于真实志愿记录生成的公开展示内容，并维护标题、展示文案、展示状态、发布时间以及点赞互动等公开传播信息。**

## 11.6 日记墙内容明确不负责的内容

日记墙内容不能：

- 自己产生志愿积分；
- 修改原志愿记录的服务类别；
- 修改原志愿记录的服务日期；
- 修改原志愿记录的服务时长；
- 修改原志愿记录的地点；
- 修改原志愿记录最终结算积分；
- 决定志愿记录本身是否有效。

因此：

> **日记墙内容不是新的志愿记录。**

---

## 15. 点赞关系对象

## 15.1 业务定位

点赞关系表达：

> **一个学生与一条日记墙内容之间的点赞关系。**

## 15.2 点赞关系存在的必要性

如果只在日记墙内容里保存：

```text
likeCount = 20
```

系统只能知道：

> 有 20 个赞。

但无法知道：

- 当前学生是否点过赞；
- 是否允许再次点赞；
- 取消点赞应该删除哪一个行为关系。

为了实现：

> **一个学生对同一条日记墙内容最多点赞一次**

必须存在可识别的学生—帖子关系。

## 15.3 点赞关系至少需要表达的信息

当前至少需要：

- 点赞学生；
- 对应日记墙内容；
- 点赞时间。

点赞时间用于表达这条关系建立的时间，具有低成本的追溯价值，当前正式纳入领域数据。

## 15.4 点赞关系当前核心职责总结

正式定义：

> **表示某名学生对某条日记墙内容建立的点赞关系，用于保证点赞唯一性并支持点赞 / 取消点赞。**

---

## 28. 志愿记录与日记墙内容的关系

当前正式确定：

> **一条志愿记录最多对应一条日记墙内容。**

业务表示：

```text
VolunteerRecord 1 ---- 0..1 DiaryPost
```

因此：

- 一条志愿记录可以不申请日记墙展示；
- 一条志愿记录可以生成一条日记墙内容；
- 不允许同一条志愿记录反复生成多条帖子。

这样可以避免同一志愿事迹重复公开展示、重复产生互动入口和额外治理复杂度。

---

## 31. 学生与日记墙内容的关系

当前确定：

> **一个学生可以发布多条日记墙内容。**

业务表示：

```text
Student 1 ---- N DiaryPost
```

虽然可以通过 `DiaryPost → VolunteerRecord → Student` 间接追溯作者，但仍保留：

> **日记墙内容 → 发布学生**

这一直接业务关系。

原因包括：

- 日记墙页面需要直接知道作者；
- 需要判断“这是不是我的帖子”；
- 当前不提供学生申请下架功能，因此不以该功能作为权限判断理由；
- 个人公开内容展示需要作者关系；
- 业务语义更加清晰。

同时正式冻结：

> **日记墙内容的发布学生必须与其关联志愿记录的所属学生完全一致。**

不允许：

```text
志愿记录属于学生 A
但日记墙内容由学生 B 发布
```

一致性约束：

```text
DiaryPost.publisher
==
DiaryPost.volunteerRecord.ownerStudent
```

---

## 32. 学生、日记墙内容与点赞关系

从业务上看：

- 一个学生可以点赞很多条日记墙内容；
- 一条日记墙内容可以被很多学生点赞。

原始关系是：

```text
Student N ---- M DiaryPost
```

由于点赞关系已经独立建模，因此正式关系为：

```text
Student 1 ---- N LikeRelation
LikeRelation N ---- 1 DiaryPost
```

也可以理解为：

```text
Student 1 ---- N LikeRelation N ---- 1 DiaryPost
```

一条点赞关系：

- 只能属于一个学生；
- 只能指向一条日记墙内容。

---

## 33. 点赞唯一性约束

正式冻结：

> **同一个学生对同一条日记墙内容最多存在一条点赞关系。**

逻辑唯一键为：

```text
(StudentId, DiaryPostId)
```

因此：

```text
点赞
= 创建一条 LikeRelation

取消点赞
= 删除对应 LikeRelation

点赞数量
= 统计该帖子当前 LikeRelation 数量
```

点赞数量仍然属于派生统计结果。

---

## 34. 学生是否允许点赞自己的帖子

当前决定：

> **允许学生点赞自己的日记墙内容。**

理由：

- 点赞只是轻量互动；
- 点赞不影响积分；
- 点赞不影响排行榜；
- 点赞不影响专项徽章；
- 点赞不影响排行称号；
- 点赞不影响默认排序。

因此没有必要增加额外禁止规则。

---

## 35. 日记墙下架与点赞关系

当前原则：

> **日记墙内容被下架时，不因为下架而删除已有点赞关系。**

因为：

> **下架 = 停止公开展示**

并不等于：

> **帖子对象不存在。**

是否允许日记墙内容物理删除，以及物理删除后点赞关系如何级联清理，暂不在本阶段冻结。

# 第六部分：操作日志与治理支撑——对应 Gate 1 治理域

## 14. 操作日志对象

## 14.1 业务定位

操作日志属于：

> **审计对象。**

它不是系统业务操作的执行者，而是：

> **关键管理行为发生之后留下的可追溯事实。**

## 14.2 操作日志至少需要表达的信息

当前至少包括：

- 操作时间；
- 操作管理员；
- 操作类型；
- 操作对象；
- 简要说明。

## 14.3 操作日志记录的行为范围

当前至少记录：

- 审核通过；
- 审核驳回；
- 修改志愿类别；
- 修改服务时长；
- 强制修正已通过记录；
- 删除志愿记录；
- 修改积分系数；
- 修改专项徽章门槛；
- 禁用学生账号；
- 恢复学生账号；
- 审核日记墙展示申请；
- 下架日记墙内容；
- 数据导出。

## 14.4 操作日志对象的业务职责

操作日志负责：

- 记录关键管理行为；
- 记录行为发生时间；
- 记录执行管理员；
- 记录操作类型；
- 记录操作目标；
- 记录简要说明；
- 为后续审计和责任追溯提供数据。

## 14.5 操作日志当前核心职责总结

正式定义：

> **记录关键管理操作的时间、执行者、对象和内容，为系统审计与责任追溯提供依据。**

## 14.6 操作日志明确不负责的内容

操作日志不负责：

- 判断某个操作是否合法；
- 执行管理员业务；
- 自动修改志愿记录；
- 自动修改积分；
- 决定用户权限。

它的定位是：

> **记录发生过什么。**

---

## 39. 管理员与操作日志的关系

当前确定：

> **一名管理员可以产生多条操作日志。**

> **一条操作日志只对应一个执行管理员。**

业务表示：

```text
Administrator 1 ---- N OperationLog
```

操作日志必须能够回答：

> **“是谁执行了这个关键操作？”**

因此：

```text
OperationLog.operator
→ Administrator
```

属于稳定业务关系。

---

## 40. 操作日志与操作对象的关系

操作日志还需要表达：

> **“操作的是谁 / 什么对象？”**

日志可能作用于不同类型业务对象，例如：

- 志愿记录；
- 学生账号；
- 志愿类别；
- 专项徽章规则；
- 学期；
- 日记墙内容；
- 数据导出行为。

因此当前只冻结业务要求：

```text
OperationLog
├── operator → Administrator
└── target   → 被操作业务对象
```

不在 Gate 2 提前决定 `target` 最终采用对象 ID + 类型、统一接口、多态引用、字符串描述还是其他 C++ 表示方式。

这些属于 Gate 3 架构决策。

## 42. Gate 2.3 已冻结硬约束

截至当前，正式冻结以下关系约束：

1. 一条志愿记录只能属于一个学生。
2. 一个学生可以拥有多条志愿记录。
3. 管理员是志愿记录的审核 / 治理主体，不是记录拥有者。
4. 志愿审核行为必须能够追溯到执行管理员。
5. 管理员与学生之间存在用户管理关联，但不存在生命周期拥有关系。
6. 一条志愿记录分别关联申报类别和最终确认类别。
7. 一种志愿类别可以被多条志愿记录使用。
8. 历史志愿记录必须独立固化结算时系数和最终积分，不能依赖当前类别系数实时重算。
9. 一条志愿记录最多对应一条日记墙内容。
10. 只有当前存在且审核通过的志愿记录才能申请生成日记墙内容。
11. 原志愿记录被管理员物理删除时，对应日记墙内容同步删除，其点赞关系同步清理。
12. 一个学生可以拥有多条日记墙内容。
13. 日记墙内容发布学生必须与关联志愿记录所属学生一致。
14. 一个学生可以点赞多条日记墙内容。
15. 一条日记墙内容可以被多个学生点赞。
16. 点赞多对多关系通过独立 `LikeRelation` 关系对象拆解。
17. 同一学生对同一日记墙内容最多存在一条点赞关系。
18. 点赞数量由点赞关系数量统计得到。
19. 允许学生点赞自己的日记墙内容。
20. 日记墙内容下架时不因下架自动删除已有点赞关系。
21. 一个专项徽章规则必须对应一个志愿类别。
22. 一个志愿类别当前最多对应一套专项徽章规则。
23. 学生当前徽章等级由当前有效数据和徽章规则动态计算，不建立永久拥有关系。
24. 学期不拥有志愿记录，只提供学期统计时间边界。
25. 一条操作日志只对应一个执行管理员。
26. 一名管理员可以产生多条操作日志。
27. 操作日志可以指向不同类型业务对象，具体技术表示方式留待 Gate 3。

当前已经完成主要领域对象之间的业务关系主体建模，明确了主要基数关系、业务归属、审核关系、配置依赖、日记墙来源约束、点赞多对多拆解、学期统计依赖和日志执行主体关系。

当前仍不在 Gate 2 中提前冻结最终 C++ 的组合/聚合实现、对象引用方式、持久化落盘方式和最终 UML 技术符号，这些继续移交 Gate 3。

## 44. Gate 2.4：数据归属审计

Gate 2.4 采用以下总原则：

> **对象保存自己的稳定业务事实；历史结算结果必须固化；可由当前有效数据与关系重新计算的结果原则上不重复持久化。**

## 44.1 学生 Student

### 自身持久数据

- 学号；
- 姓名；
- 班级；
- 专业；
- 联系方式；
- 账号状态；
- 创建时间；
- 最后登录时间；
- 密码相关信息。

### 业务归属关系

学生还具有：

- `0..N` 条自己的志愿记录；
- `0..N` 条自己的日记墙内容；
- `0..N` 条自己建立的点赞关系。

这里的“归属关系”不代表把 `VolunteerRecord`、`DiaryPost`、`LikeRelation` 的完整字段复制到 `Student` 内。最终采用容器、对象引用、指针、智能指针还是 ID，由 Gate 3 决定。

以下不作为 Student 中可独立修改的持久事实：

- 月度积分；
- 学期积分；
- 总积分；
- 当前月度/学期/总榜排名；
- 当前排行榜称号；
- 当前专项徽章等级；
- 当前各类别有效服务时长；
- 当前有效服务总时长。

## 44.2 管理员 Administrator

管理员自身持久数据：

- 管理员账号；
- 姓名；
- 账号状态；
- 密码相关信息。

管理员对志愿记录、学生、类别、徽章规则、学期、日记墙等具有管理权限，但：

> **有权限操作某类数据 ≠ 该数据应该存进管理员对象。**

各业务数据继续归其对应领域对象管理，避免 `Administrator` 变成“上帝类”。

---

## 44.3 志愿记录 VolunteerRecord

志愿记录持久数据分为三组事实加一个状态组。

### 学生申报事实

- 记录编号；
- 所属学生；
- 服务日期；
- 申报类别；
- 申报时长；
- 地点；
- 证明人；
- 简述。

### 审核结果

- 审核状态；
- 审核管理员；
- 审核意见；
- 最终确认类别；
- 最终确认时长。

### 历史结算快照

审核通过后必须固化：

- 结算时实际使用的积分系数；
- 最终结算积分。

原因是历史已结算记录不能随当前类别系数变化而被追溯重算。

### 状态规则

志愿记录只保留：

- 待审核；
- 已通过；
- 已驳回；
- 已撤回。

明确不设置：

- 已删除；
- 已失效；
- `isDeleted`；
- `isValid`。

删除不是状态，而是对象不再存在。管理员删除志愿记录时：

1. 写入删除原因与操作日志；
2. 物理删除 `VolunteerRecord`；
3. 同步删除关联 `DiaryPost`；
4. 同步清理对应 `LikeRelation`；
5. 重新计算积分、排行榜、排行称号和专项徽章。

---

## 44.4 志愿类别 VolunteerCategory

持久数据：

- 类别名称；
- 当前积分系数；
- 启用状态。

不保存某学生积分、类别全局服务总时长、类别记录数量、学生当前徽章等级等统计结果。

历史已结算记录使用的系数和积分已经固化在 `VolunteerRecord` 中，因此类别当前系数只影响后续新的结算行为。

---

## 44.5 专项徽章规则 BadgeRule

持久数据：

- 徽章名称；
- 对应志愿类别；
- 铜级门槛；
- 银级门槛；
- 金级门槛；
- 启用状态。

专项徽章仅指按照某一志愿类别累计有效服务时长判定的六类徽章：

- 劳动先锋；
- 互助之星；
- 公益传播者；
- 环保卫士；
- 暖心使者；
- 校园协力者。

明确：

> **专项徽章体系不包含月度积分徽章、学期积分徽章或总积分累计徽章。**

积分维度的荣誉由排行榜称号承担：

- 月度雷锋之星·金/银/铜；
- 学期志愿先锋·金/银/铜；
- 雷锋标兵·金/银/铜。

因此两条荣誉主线保持分工：

```text
专项徽章
→ 看某个志愿类别中的长期专项投入
→ 依据有效服务时长

排行榜称号
→ 看月度 / 学期 / 总积分综合排名
→ 依据排行榜名次
```

`BadgeRule` 不保存“哪些学生获得了徽章”或“某学生当前徽章等级”，这些继续动态判定。

---

## 44.6 日记墙内容 DiaryPost

持久数据：

- 内容编号；
- 关联志愿记录；
- 发布学生；
- 展示标题；
- 展示文案；
- 展示状态；
- 正式公开时间。

此前使用的“正式公开时间”统一改名为：

> **正式公开时间**

其含义是：

> **管理员通过日记墙展示审核、帖子正式进入公开信息流的时刻。**

它不是“帖子可以展示到什么时候”。当前系统不设置自动过期时间、展示截止时间或固定展示期限。

状态与时间关系：

```text
待展示审核
→ 正式公开时间为空

管理员通过展示审核
→ 展示状态 = 已展示
→ 写入正式公开时间

帖子下架
→ 展示状态 = 已下架
→ 正式公开时间仍然保留
```

正式公开时间同时作为日记墙默认“按正式公开时间倒序”排序的依据。

### 点赞数量

点赞数量不作为 `DiaryPost` 的独立持久事实。

```text
当前点赞数
=
该 DiaryPost 对应的 LikeRelation 数量
```

这样避免同时维护点赞关系和 `likeCount` 两份重复数据。

日记墙展示出来的学生姓名、志愿类别、服务日期、服务时长、地点和本条积分等事实继续从关联的 `VolunteerRecord` 读取，不在 `DiaryPost` 中复制一份。

---

## 44.7 学期 Semester

持久数据：

- 学期名称；
- 开始日期；
- 结束日期；
- 是否当前学期。

不保存：

- 某学生学期积分；
- 学期排行榜；
- 学期前三名；
- 学期排行榜称号。

这些均由学期时间范围和审核通过志愿记录动态计算。

---

## 44.8 点赞关系 LikeRelation

持久数据：

- 点赞学生；
- 对应日记墙内容；
- 点赞时间。

点赞时间不是保证点赞唯一性的绝对必需字段，但具有明确的关系时间语义和低成本追溯价值，因此纳入当前领域数据。

逻辑唯一键继续为：

```text
(StudentId, DiaryPostId)
```

点赞 = 创建一条 `LikeRelation`；取消点赞 = 删除对应 `LikeRelation`；帖子点赞数 = 统计当前关系数量。

---

## 44.9 操作日志 OperationLog

持久数据：

- 日志编号；
- 操作时间；
- 操作管理员；
- 操作类型；
- 操作对象；
- 简要说明。

新增“日志编号”，用于唯一定位、查询、导出与审计引用。

对于删除志愿记录等关键操作，可以通过“操作对象 + 简要说明”保留被删除记录编号、删除原因等必要信息，不为每种操作机械增加大量专用字段。

## 50. Gate 2.5：领域边界与最终审计

2. Gate 1 → Gate 2 需求责任映射审计。

目标是确认：

> **Gate 1 中已经冻结的每一类业务需求，在 Gate 2 中都有明确的领域对象或派生计算机制承接。**

## 50.1 最终领域对象集合

当前领域模型保留 9 个对象。

核心业务对象：

- `Student`
- `Administrator`
- `VolunteerRecord`
- `VolunteerCategory`
- `DiaryPost`

配置 / 支撑对象：

- `BadgeRule`
- `Semester`
- `OperationLog`

关系对象：

- `LikeRelation`

经过审计，没有发现必须新增的领域对象。

同时，不为了课程最低类数量要求机械新增“积分类”“排行榜类”“统计类”等无独立生命周期的实体。

## 50.2 Student / Administrator 边界

`Student`：

> 学生身份主体 + 学生业务发起主体。

`Administrator`：

> 管理身份主体 + 审核、治理、配置行为执行主体。

领域层只说明“谁承担什么业务责任”，不在 Gate 2 决定最终 C++ 是否采用统一 `User` 基类。

统一基类、继承和多态设计正式移交 Gate 3。

结论：

**PASS**

## 50.3 VolunteerRecord 边界

`VolunteerRecord` 只负责：

```text
申报事实
+
审核结果
+
历史结算快照
+
待审核 / 已通过 / 已驳回 / 已撤回 四状态生命周期
```

不负责：

- 全局积分汇总；
- 排行榜；
- 专项徽章规则；
- 日记墙展示文案；
- 用户管理。

术语统一：

> 后续优先使用“当前存在的已通过志愿记录”或“已通过志愿记录”。

不再把“已删除 / 已失效”当作记录仍然存在时的业务状态。

结论：

**PASS**

## 50.4 VolunteerCategory / BadgeRule 边界

`VolunteerCategory` 负责类别名称、当前积分系数和启用状态。

`BadgeRule` 负责某一志愿类别对应的专项徽章名称、铜 / 银 / 金门槛和启用状态。

学生积分、类别总时长、当前徽章等级等均不归规则对象直接保存。

专项徽章只评价某一类别的长期专项投入。积分维度荣誉由排行榜称号承担，不新增月度 / 学期 / 总积分徽章实体。

结论：

**PASS**

## 50.5 DiaryPost / LikeRelation 边界

`DiaryPost` 负责帖子自身的标题、展示文案、展示状态、正式公开时间，以及与原志愿记录和发布学生的关联。

`LikeRelation` 负责谁点赞、点赞哪一条、点赞时间。

点赞数量由 `LikeRelation` 数量动态统计。

帖子展示中的志愿类别、服务日期、服务时长、地点和结算积分等真实业务事实从关联 `VolunteerRecord` 获取，不重复保存。

结论：

**PASS**

## 50.6 Semester / OperationLog 边界

`Semester` 只提供学期时间范围与当前学期配置，不保存学期积分、排行榜或学期称号。

`OperationLog` 只记录关键管理行为已经发生的审计事实，不执行操作、不判断权限、不保存被操作对象的完整副本。

结论：

**PASS**

## 50.7 是否需要独立审核历史对象

专门审计是否新增：

- `ReviewRecord`
- `AuditRecord`

当前不新增。

现阶段：

```text
VolunteerRecord
→ 保存当前审核状态、审核管理员、审核意见

OperationLog
→ 保存关键审核 / 治理事件的历史追溯信息
```

已经满足当前课程设计业务需求。

如果未来需求升级为“完整恢复每一次审核版本和全部历史快照”，再考虑独立审核历史对象。

结论：

**当前不新增审核历史实体。**
