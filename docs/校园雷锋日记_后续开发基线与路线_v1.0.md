# 2. 后续开发总原则

## 2.1 不机械补齐全部历史功能

此前 Gate 1～4 中设计过的功能很多，后续不以“全部实现”为目标。

筛选标准统一为：

1. 是否明显提升核心业务完整性；
2. 是否明显提升课程展示与答辩价值；
3. 是否能体现面向对象、分层、状态、数据一致性等设计能力；
4. 是否对后续 Qt / 云端化有帮助；
5. 实现成本是否与收益匹配；
6. 是否会造成不必要的复杂化或过度设计。

原则：

> **宁可做少而完整的高价值功能，也不做大量低收益页面和配置项。**

---

## 2.2 Qt 与业务功能同步演进

以后新增任何正式业务功能，都必须同步设计对应 Qt 表现层。

不采用：

```text
先把所有后端功能补完
↓
最后统一补 Qt
```

采用纵向切片：

```text
Domain / Service / Repository
↓
Persistence
↓
Qt Page / Dialog
↓
Build
↓
Test
↓
Regression
↓
Audit
↓
PASS
```

一个功能包完成完整闭环后，再进入下一个功能包。

---

## 2.3 不无限细化

后续优先处理：

- 核心功能缺失；
- 明显架构问题；
- 数据一致性问题；
- 编译 / 运行问题；
- 可复现性问题；
- 重要 UI / 交互问题；
- 云端化前置问题。

不为了“看起来更复杂”持续增加：

- 无实际需求的类；
- 无实际需求的设计模式；
- 复杂权限编辑器；
- 多余配置中心；
- 大量低价值后台 CRUD；
- 无性能证据的缓存或索引。

# 6. 核心架构整理

当前版本已有 Qt 与业务闭环，但底层仍偏集中。

后续逐步靠近：

```text
Qt Presentation
      ↓
Application / Service
      ↓
Domain + Repository
      ↓
Persistence
```

目标不是一次性“大重构”，而是：

- 新功能优先按新分层实现；
- 旧逻辑在真实改动涉及到时逐步迁移；
- Qt 不继续直接承担业务规则；
- 业务逻辑不复制到多个页面；
- Repository / Persistence 与 Service 逐步分离；
- stable ID 继续作为跨层对象身份。

# 10. 云端共享数据库目标

最终联网目标：

> 多台电脑运行同一个 Qt 客户端，并访问同一份云端权威业务数据。

目标效果：

```text
Qt Client A ─┐
Qt Client B ─┼─ HTTPS ─→ Backend API ─→ Cloud Database
Qt Client C ─┘
```

示例：

```text
电脑 A：学生提交志愿记录
↓
云端保存
↓
电脑 B：管理员刷新后立即看到
↓
管理员审核
↓
电脑 A：刷新后看到最新审核结果与积分
```

# 11. 云端架构原则

## 11.1 Qt 不直接暴露数据库连接

不建议：

```text
Qt.exe
↓
公网 MySQL / PostgreSQL
```

原因：

- 数据库账号和密码容易暴露在客户端；
- 数据库权限难控制；
- 客户端可以绕过业务规则；
- 后续扩展与安全性差。

采用：

```text
Qt
↓ HTTPS
Backend API
↓
Cloud Database
```

---

## 11.2 保留本地演示能力

最终理想状态：

```text
               ┌── Local Mode
Qt → Service ──┤
               └── Cloud Mode
```

目的：

- 老师离线也能直接运行；
- 云端服务不可用时仍能演示；
- release 包保持可复现；
- 云端模式用于展示多设备共享数据。

---

## 11.3 云端化需要重新进行架构审计

当前历史 Gate 3 的 Repository 设计建立在“只有本地文件后端”的前提上。

一旦真实出现：

```text
Local Persistence
+
Remote Backend
```

存储后端数量已经发生变化。

因此云端化必须显式重新审计：

- Repository 抽象是否需要调整；
- Local / Remote 模式如何切换；
- Service 是否保持不变；
- API 边界；
- 认证方式；
- 并发写入；
- 错误处理；
- 网络不可用；
- 数据同步；
- 本地与云端谁是权威数据源。

不得偷偷用数据库实现覆盖已有架构语义。

# 14. 当前冻结结论

截至本文件 v1.0，后续开发方向暂定为：

> **以当前提交版为真实开发基线；优先建立 GitHub 版本管理并完成 Qt UI 2.0；随后逐步整理 Service / Repository 等核心分层；业务扩展只实现审核增强、学期统计与三类排行榜、OperationLog、日记墙管理员治理、学生账号管理五个高价值功能包；时间允许时增加 CSV / Markdown Export；每个业务功能必须同步完成对应 Qt；本地完整稳定版完成后，再单独进入 Cloud Backend + Shared Database 架构阶段，同时保留本地离线演示能力。**

本结论用于约束后续开发，不代表推翻 Gate 1～4 历史设计文档。

如未来真实实现发现：

- 当前功能组合不合理；
- 云端化要求改变；
- 某个精选功能收益不足；
- 某项实现与 Gate 冻结架构出现真实冲突；

应通过显式审计和版本修订更新本文件，不无痕覆盖。
