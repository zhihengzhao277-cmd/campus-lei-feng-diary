# 2. 后续开发总原则

## 2.1 不机械补齐全部历史功能

此前 Gate 1～4 中设计过的功能很多，后续不以“全部实现”为目标。

筛选标准统一为：

1. 是否明显提升核心业务完整性；
2. 是否明显提升课程展示与答辩价值；
3. 是否能体现面向对象、分层、状态、数据一致性等设计能力；
4. 是否对后续 Qt / 云端化有帮助；
5. 实现成本是否与收益匹配；
6. 是否会造成不必要的复杂化或过度设计。

原则：

> **宁可做少而完整的高价值功能，也不做大量低收益页面和配置项。**

---

## 2.2 Qt 与业务功能同步演进

以后新增任何正式业务功能，都必须同步设计对应 Qt 表现层。

不采用：

```text
先把所有后端功能补完
↓
最后统一补 Qt
```

采用纵向切片：

```text
Domain / Service / Repository
↓
Persistence
↓
Qt Page / Dialog
↓
Build
↓
Test
↓
Regression
↓
Audit
↓
PASS
```

一个功能包完成完整闭环后，再进入下一个功能包。

---

## 2.3 不无限细化

后续优先处理：

- 核心功能缺失；
- 明显架构问题；
- 数据一致性问题；
- 编译 / 运行问题；
- 可复现性问题；
- 重要 UI / 交互问题；
- 云端化前置问题。

不为了“看起来更复杂”持续增加：

- 无实际需求的类；
- 无实际需求的设计模式；
- 复杂权限编辑器；
- 多余配置中心；
- 大量低价值后台 CRUD；
- 无性能证据的缓存或索引。

---

## 2.4 课程设计尺度下的通用审计标准

本项目后续所有实现、审计与路线裁决统一采用以下尺度：

> **以当前提交版为真实基础做高收益优化，向 Gate 冻结的优秀架构方向靠近，但不以“完整复刻 Gate 1～4”作为目标。**

Gate 文档在当前路线中的作用是：

```text
需求 / 架构方向
+
边界与禁止项
+
发生冲突时的裁决依据
```

而不是：

```text
必须逐条实现的企业级施工清单
```

因此，一个候选改动是否进入正式 IU，优先回答：

1. 是否解决当前代码中的真实 Bug、真实耦合或真实一致性问题；
2. 是否明显提升课程要求中的正确性、面向对象设计、可维护性、可复现性或答辩展示价值；
3. 是否为已经选定的后续高价值功能提供必要前置能力；
4. 是否能在合理工作量内完成完整 build / test / regression / audit 闭环；
5. 是否会引入明显高于当前课程项目收益的复杂度；
6. 如果不做，是否真的阻塞后续路线。

只有前四项收益明确、且第五项成本可接受时，才优先实施。

### 当前核心架构整理的六类优先问题

当前优先围绕以下六类真实问题审计和选择性实施：

1. Qt → Service 业务边界；
2. ApplicationContext / 统一 MainWindow 的重复职责与生命周期；
3. Diary Public View、作者权威派生与公开荣誉边界；
4. `BUG-RUNTIME-001` 与稳定 Runtime Data Root；
5. 认证 / 密码安全债务；
6. DataManager / DataList 等历史架构债务中真正影响后续开发的部分。

这六类是“优先审计范围”，不是“必须全部做成完整版”的承诺。

### 明确禁止过度工程化

除非当前真实需求、Bug 或已选功能明确需要，否则不主动引入或追求：

- 企业级 DI / Service Locator / ORM / 微服务式拆分；
- 为形式完整而建立大量一对一包装类、接口或 Generic Repository 框架；
- 复杂缓存、多级索引、数据库级优化；
- 不必要的分布式事务、企业级容灾或无限故障注入；
- 以覆盖率数字为目标的大规模测试体系；
- 为追求“理论最纯”而大范围重写已经稳定运行的代码；
- 只因为完整版 / Gate 中存在，就机械增加当前项目并不需要的类、字段、页面或模式。

测试的定位是：

> **为当前重构提供足够的回归安全网，而不是建设企业级 QA 平台。**

架构整理的定位是：

> **解决当前最值得解决的问题，让结构明显变好并为后续精选功能让路，而不是追求架构完美。**

### 审计收口与 reopen 规则

一个 IU 在以下条件满足后应 PASS 并冻结：

- 当前范围目标已经完成；
- build / test / 必要人工回归通过；
- 没有已知阻塞性缺陷；
- 没有违反当前权威边界；
- 继续微调的收益已经明显低于成本。

PASS 后不重复设计。只有出现以下情况才允许 reopen：

- 真实 Bug；
- 已通过功能发生回归；
- 新实现暴露当前权威冲突；
- 新的明确课程 / 业务需求；
- 后续功能证明原冻结点确实成为阻塞。

不得因为“还可以更优雅”“企业项目一般会继续做”而无限 reopen。

### 当前阶段的“足够好”标准

当一个架构切片已经做到：

```text
行为正确
+
职责比提交版明显清楚
+
关键规则不再重复漂移
+
有最小自动化安全网
+
Qt / Console 主要路径可回归
+
后续精选功能不再被它阻塞
```

即可认为达到本课程项目当前阶段的合理完成标准。

不继续为了企业级完整性做低收益扩张。

# 5. Qt UI 2.0

UI 2.0 不只是换颜色。

目标：

> **把当前“功能齐全的 Qt 页面”升级为风格统一、结构清楚、适合答辩展示的完整桌面应用。**

第一轮执行策略（已完成）：

> **第一轮 UI 2.0 优先做 Presentation 视觉与局部结构优化，保持现有业务行为不变；统一 MainWindow、ApplicationContext、Service 化等结构性工作作为目标架构保留，不与第一轮视觉改造强行混在同一个 IU 中。**

这样可以避免同时修改视觉、生命周期和业务边界后难以定位回归问题。

### 5.6.1 徽章图标设计原则

沿用当前三类专项荣誉：


沿用当前等级：



### 5.6.2 徽章资源归属

徽章图标属于：

```text
Qt Presentation Resource
```

不属于：

```text
Domain
Repository
Persistence schema
```

禁止为了显示图标就在 Domain 中加入：

```text

imageFile
QPixmap
QIcon
```

等表现层字段。

推荐：

```text
业务层 / Query Result
→ 提供 badge identity / 名称 / 等级

Qt Presentation
→ 根据 badge identity 映射本地资源
→ 展示对应徽章图标
```

资源后续统一放入类似：

```text
qt/resources/badges/
```

并使用 Qt Resource System 管理。

优先采用不会额外引入大型 UI / 运行时依赖的本地图片资源。

# 6. 核心架构整理

Qt UI 2.0 第一轮完成后，不直接继续堆功能，而进入一次显式核心架构整理。

目标仍是：

```text
Qt Presentation
      ↓
Application / Service
      ↓
Domain + Repository
      ↓
Persistence
```

原则：

- 不一次性推倒重写；
- 新功能优先按目标分层实现；
- 旧代码按真实改动范围迁移；
- 不为了“架构好看”制造大量无业务价值抽象；
- 所有 Gate 冲突继续使用 STOP-14 显式处理。

---

## 6.1 UI / Application 边界

当前债务：

```text
StudentMainWindow / AdministratorMainWindow
→ 直接持有 DataManager
→ 部分页面直接执行业务查询 / 修改
```

后续逐步迁移：

```text
Qt Page / Dialog
→ Service
→ Domain / Repository
```

Qt 不继续新增跨领域业务算法。

---

## 6.2 MainWindow / ApplicationContext

长期冻结目标仍是：

```text
LoginWindow
↓
ApplicationContext
↓
统一 MainWindow / Application Shell
```

当前双主窗已经产生明显重复：

- 顶部用户区；
- Sidebar；
- logout；
- Profile；
- 公共 Ranking / DiaryWall 能力；
- 页面容器。

但不要求在 UI 2.0 阶段立即合并。

核心架构整理时再渐进收敛。

## 6.3 Diary 公开查询边界 —— 高优先级

这是 IU-UI-07 STOP-14 后明确形成的优先任务。

```text
↓

↓
DiaryWallPage
↓
```

```text
↓

```

同时由 Query / Application 层组装：

- 正文；
- 点赞状态 / 点赞数；
- 雷锋之星；
- 专项徽章。

Qt 不自行跨多个 Domain / Service 拼接这些事实。

### Diary schema 差距

Gate 设计中存在比当前提交版更完整的 DiaryPost 目标字段。

当前路线不允许在 UI IU 中顺手补 schema。

如果核心架构整理发现必须新增：

- title；
- display status；
- publishedAt；
- LikeRelation 独立对象；

必须按独立 IU / STOP 审计，不无痕增加。

## 6.4 BUG-RUNTIME-001 —— 数据路径依赖

当前真实 Bug：

```text
DataManager
→ 使用 data/students.txt
→ 使用 data/administrators.txt
→ 使用其他 data/... 相对路径
```

这些路径相对于：

```text
process working directory
```

而不是稳定 Runtime Data Root。

复现：

```text
从 build 目录作为 working directory 启动
→ 找不到项目根目录 data/
→ Student / Administrator 加载为空
→ 所有合法账号均表现为“账号或密码错误”
```

当前 workaround：

```text
从项目根目录作为 working directory 启动
```

状态：

```text
BUG-RUNTIME-001
OPEN / DEFERRED
```

该问题应在 Persistence / runtime-path 整理中正式解决，并补：

- 明确 runtime data root；
- Development / Release 的统一定位策略；
- 缺失数据文件时不能伪装成“账号密码错误”；
- 回归 build 目录 / release 目录 / 独立复制目录。

---

## 6.5 安全与认证债务

当前提交版仍保留 Legacy 明文密码持久化。

Gate4 已冻结更高标准的密码实现方向。

因此：

> **在最终声称高标准 Gate 对齐前，认证 / 密码存储必须进行独立审计与实现决策。**

不得在普通 UI IU 中顺手改密码 schema。

该项放入核心架构 / 安全整理阶段，由独立 IU 决定是否完整落地。

## 6.6 其他已知架构债务

后续核心整理至少需要重新审计：

- `DataManager` 同时承担数据、查询、业务与持久化；
- Qt 直接访问 `DataManager`；
- Student / Administrator 双 MainWindow 重复；
- Legacy `DiaryCardWidget` 持有 `DiaryPost*`；
- 当前文件持久化仍为轻量 txt / delimiter 方案；
- 当前自定义 `DataList<T>` 与 Gate 最终 `Result<T>` 模板路线存在历史差距；
- 当前程序与最终 Gate 的 AccountStatus / Permission / Service / Repository / Result 等结构仍有实现差距。

这些差距：

> **需要审计，但不等于自动授权“全部 Gate 功能一次性重写”。**

仍按高价值、必要性和真实风险逐项推进。

# 10. 云端共享数据库目标

最终联网目标：

> 多台电脑运行同一个 Qt 客户端，并访问同一份云端权威业务数据。

目标效果：

```text
Qt Client A ─┐
Qt Client B ─┼─ HTTPS ─→ Backend API ─→ Cloud Database
Qt Client C ─┘
```

示例：

```text
电脑 A：学生提交志愿记录
↓
云端保存
↓
电脑 B：管理员刷新后立即看到
↓
管理员审核
↓
电脑 A：刷新后看到最新审核结果与积分
```

---

# 11. 云端架构原则

## 11.1 Qt 不直接暴露数据库连接

不建议：

```text
Qt.exe
↓
公网 MySQL / PostgreSQL
```

原因：

- 数据库账号和密码容易暴露在客户端；
- 数据库权限难控制；
- 客户端可以绕过业务规则；
- 后续扩展与安全性差。

采用：

```text
Qt
↓ HTTPS
Backend API
↓
Cloud Database
```

---

## 11.2 保留本地演示能力

最终理想状态：

```text
               ┌── Local Mode
Qt → Service ──┤
               └── Cloud Mode
```

目的：

- 老师离线也能直接运行；
- 云端服务不可用时仍能演示；
- release 包保持可复现；
- 云端模式用于展示多设备共享数据。

---

## 11.3 云端化需要重新进行架构审计

当前历史 Gate 3 的 Repository 设计建立在“只有本地文件后端”的前提上。

一旦真实出现：

```text
Local Persistence
+
Remote Backend
```

存储后端数量已经发生变化。

因此云端化必须显式重新审计：

- Repository 抽象是否需要调整；
- Local / Remote 模式如何切换；
- Service 是否保持不变；
- API 边界；
- 认证方式；
- 并发写入；
- 错误处理；
- 网络不可用；
- 数据同步；
- 本地与云端谁是权威数据源。

不得偷偷用数据库实现覆盖已有架构语义。
