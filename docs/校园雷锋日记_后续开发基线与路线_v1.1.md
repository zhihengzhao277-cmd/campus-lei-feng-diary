# 2. 后续开发总原则

## 2.1 不机械补齐全部历史功能

此前 Gate 1～4 中设计过的功能很多，后续不以“全部实现”为目标。

筛选标准统一为：

1. 是否明显提升核心业务完整性；
2. 是否明显提升课程展示与答辩价值；
3. 是否能体现面向对象、分层、状态、数据一致性等设计能力；
4. 是否对后续 Qt / 云端化有帮助；
5. 实现成本是否与收益匹配；
6. 是否会造成不必要的复杂化或过度设计。

原则：

> **宁可做少而完整的高价值功能，也不做大量低收益页面和配置项。**

---

## 2.2 Qt 与业务功能同步演进

以后新增任何正式业务功能，都必须同步设计对应 Qt 表现层。

不采用：

```text
先把所有后端功能补完
↓
最后统一补 Qt
```

采用纵向切片：

```text
Domain / Service / Repository
↓
Persistence
↓
Qt Page / Dialog
↓
Build
↓
Test
↓
Regression
↓
Audit
↓
PASS
```

一个功能包完成完整闭环后，再进入下一个功能包。

---

## 2.3 不无限细化

后续优先处理：

- 核心功能缺失；
- 明显架构问题；
- 数据一致性问题；
- 编译 / 运行问题；
- 可复现性问题；
- 重要 UI / 交互问题；
- 云端化前置问题。

不为了“看起来更复杂”持续增加：

- 无实际需求的类；
- 无实际需求的设计模式；
- 复杂权限编辑器；
- 多余配置中心；
- 大量低价值后台 CRUD；
- 无性能证据的缓存或索引。

# 5. Qt UI 2.0

UI 2.0 不只是换颜色。

目标：

> **把当前“功能齐全的 Qt 页面”升级为风格统一、结构清楚、适合答辩展示的完整桌面应用。**

当前执行策略：

> **第一轮 UI 2.0 优先做 Presentation 视觉与局部结构优化，保持现有业务行为不变；统一 MainWindow、ApplicationContext、Service 化等结构性工作作为目标架构保留，但不与第一轮视觉改造强行混在同一个 IU 中。**

这样可以避免同时修改视觉、生命周期和业务边界后难以定位回归问题。

---

## 5.1 全局应用壳

长期目标继续是：

```text
LoginWindow
↓
MainWindow / Application Shell
├── Sidebar
├── Header
└── PageContainer
```

后续页面逐步从巨大 MainWindow 中拆分。

但当前 UI 2.0 第一轮不要求立即把：

```text
StudentMainWindow
+
AdministratorMainWindow
```

一次性合并。

采用：

```text
先统一视觉与页面体验
↓
再进行核心架构整理
↓
再逐步收敛统一 MainWindow / Application Shell
```

不进行一次性 Qt 大重写。

## 5.2 冻结视觉规范

Qt UI 2.0 当前统一使用：

| 用途 | 冻结值 |
|---|---|
| Primary | `#B91C3A` |
| Accent | `#C58A24` |
| Background | `#F5F6F8` |
| Surface / Card | `#FFFFFF` |
| Text Primary | `#24262B` |
| Text Secondary | `#68717D` |
| Border | `#E4E7EC` |
| Success | `#2F855A` |
| Warning | `#B7791F` |
| Error | `#C2413A` |
| Info | `#2F6F9F` |

约束：

- `#B91C3A` 是全局品牌主色；
- `#C58A24` 只用于徽章、排行榜、荣誉等少量强调，不与主色竞争；
- 状态必须同时显示文字，不允许只靠颜色区分。

字号层级：

```text
Page title      18–20 pt
Section title   13–15 pt
Body / Table    10–11 pt
Secondary        9–10 pt
Stat number     24–28 pt
```

间距层级：

```text
4 / 8 / 12 / 16 / 24 / 32
```

圆角：

```text
普通控件    8 px
卡片       12 px
大型容器   16 px
```

整体视觉定位：

> **现代、干净的校园公益管理系统。**

不做成企业后台模板，也不把整个系统做成内容社区；仅日记墙允许更明显的卡片信息流风格。

## 5.6 徽章视觉体系与公开荣誉展示

徽章作为 UI 2.0 的正式视觉能力加入后续路线。

目标：

> **每一个实际徽章都有自己的小徽章图标，并且徽章不只存在于“我的徽章”页面，还能作为学生的公开荣誉在合适场景展示。**

### 5.6.1 徽章图标设计原则

沿用当前三类专项荣誉：

```text
C01 劳动类
→ 劳动先锋
→ 中央图案使用劳动 / 工具 / 手套等主题

C02 环保类
→ 环保卫士
→ 中央图案使用绿叶 / 幼苗等主题

C03 互助类
→ 互助之星
→ 中央图案使用握手 / 爱心等主题
```

沿用当前等级：

```text
铜级
银级
金级
```

当前基线对应时长阈值继续保持：

```text
10 h  → 铜级
30 h  → 银级
60 h  → 金级
```

UI 2.0 不在视觉阶段修改这些业务阈值。

设计方法：

```text
徽章类别
→ 决定中央主题图案

徽章等级
→ 决定外框 / 材质 / 等级视觉
```

因此形成一套统一体系，而不是 9 张风格互不相关的图片。

---

### 5.6.2 徽章资源归属

徽章图标属于：

```text
Qt Presentation Resource
```

不属于：

```text
Domain
Repository
Persistence schema
```

禁止为了显示图标就在 Domain 中加入：

```text
iconPath
imageFile
QPixmap
QIcon
```

等表现层字段。

推荐：

```text
业务层 / Query Result
→ 提供 badge identity / 名称 / 等级

Qt Presentation
→ 根据 badge identity 映射本地资源
→ 展示对应徽章图标
```

资源后续统一放入类似：

```text
qt/resources/badges/
```

并使用 Qt Resource System 管理。

优先采用不会额外引入大型 UI / 运行时依赖的本地图片资源。

---

### 5.6.3 我的徽章 / Achievement 页面

Achievement 页面负责完整展示。

每个徽章采用卡片形式，例如：

```text
┌────────────────┐
│      [徽章]     │
│   金级劳动先锋   │
│                │
│      已获得     │
│ 累计已通过 xx h │
└────────────────┘
```

建议：

- 主徽章图标约 `72–96 px`；
- 已获得徽章正常显示；
- 未获得徽章可灰化；
- 同时显示下一等级进度；
- 等级、名称和图标必须一致。

这里允许显示本人累计时长，因为是学生自己的 Achievement 页面。

### 5.6.4 Student Dashboard

学生主页增加：

```text
我的荣誉
```

小型区域。

只展示已经获得的代表性徽章，例如：

- 当前最高等级；
- 或最多 3 个代表徽章。

Dashboard 不重复完整徽章页，只提供荣誉概览和入口。

### 5.6.5 Ranking

排行榜允许在学生姓名附近显示小型公开荣誉徽章。

示意：

```text
1  张三   [劳动金] [环保银] [互助铜]   128.5
2  李四   [劳动银] [环保铜]             113.0
```

约束：

- 单行最多直接展示 3 个小徽章；
- 超过时使用 `+N` 等紧凑提示；
- 不让徽章破坏排行榜主要信息层级；
- 排名业务排序仍由业务层决定，徽章只是 Presentation 荣誉展示。

---

### 5.6.6 Diary Wall

日记墙将徽章作为公开荣誉的一部分。

示意：

```text
张三
[金级劳动先锋] [银级环保卫士]

今天参加了校园清洁志愿活动……
                                      ♡ 18
```

公开展示只允许：

```text

徽章名称
徽章等级
```

不因为展示徽章而公开：

```text
对方的后台志愿记录
完整累计时长
内部审核信息
其他非公开字段
```

DiaryWall / DiaryPostCard 后续仍应通过公开 View 获取必要荣誉信息，不自行跨多个领域对象拼接后台数据。

# 6. 核心架构整理

当前版本已有 Qt 与业务闭环，但底层仍偏集中。

后续逐步靠近：

```text
Qt Presentation
      ↓
Application / Service
      ↓
Domain + Repository
      ↓
Persistence
```

目标不是一次性“大重构”，而是：

- 新功能优先按新分层实现；
- 旧逻辑在真实改动涉及到时逐步迁移；
- Qt 不继续直接承担业务规则；
- 业务逻辑不复制到多个页面；
- Repository / Persistence 与 Service 逐步分离；
- stable ID 继续作为跨层对象身份。

# 10. 云端共享数据库目标

最终联网目标：

> 多台电脑运行同一个 Qt 客户端，并访问同一份云端权威业务数据。

目标效果：

```text
Qt Client A ─┐
Qt Client B ─┼─ HTTPS ─→ Backend API ─→ Cloud Database
Qt Client C ─┘
```

示例：

```text
电脑 A：学生提交志愿记录
↓
云端保存
↓
电脑 B：管理员刷新后立即看到
↓
管理员审核
↓
电脑 A：刷新后看到最新审核结果与积分
```

# 11. 云端架构原则

## 11.1 Qt 不直接暴露数据库连接

不建议：

```text
Qt.exe
↓
公网 MySQL / PostgreSQL
```

原因：

- 数据库账号和密码容易暴露在客户端；
- 数据库权限难控制；
- 客户端可以绕过业务规则；
- 后续扩展与安全性差。

采用：

```text
Qt
↓ HTTPS
Backend API
↓
Cloud Database
```

---

## 11.2 保留本地演示能力

最终理想状态：

```text
               ┌── Local Mode
Qt → Service ──┤
               └── Cloud Mode
```

目的：

- 老师离线也能直接运行；
- 云端服务不可用时仍能演示；
- release 包保持可复现；
- 云端模式用于展示多设备共享数据。

---

## 11.3 云端化需要重新进行架构审计

当前历史 Gate 3 的 Repository 设计建立在“只有本地文件后端”的前提上。

一旦真实出现：

```text
Local Persistence
+
Remote Backend
```

存储后端数量已经发生变化。

因此云端化必须显式重新审计：

- Repository 抽象是否需要调整；
- Local / Remote 模式如何切换；
- Service 是否保持不变；
- API 边界；
- 认证方式；
- 并发写入；
- 错误处理；
- 网络不可用；
- 数据同步；
- 本地与云端谁是权威数据源。

不得偷偷用数据库实现覆盖已有架构语义。
