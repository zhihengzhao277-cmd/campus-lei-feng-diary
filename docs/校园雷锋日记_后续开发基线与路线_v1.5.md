# 2. 后续开发总原则

## 2.1 不机械补齐全部历史功能

此前 Gate 1～4 中设计过的功能很多，后续不以“全部实现”为目标。

筛选标准统一为：

1. 是否明显提升核心业务完整性；
2. 是否明显提升课程展示与答辩价值；
3. 是否能体现面向对象、分层、状态、数据一致性等设计能力；
4. 是否对后续 Qt / 云端化有帮助；
5. 实现成本是否与收益匹配；
6. 是否会造成不必要的复杂化或过度设计。

原则：

> **宁可做少而完整的高价值功能，也不做大量低收益页面和配置项。**

---

## 2.2 Qt 与业务功能同步演进

以后新增任何正式业务功能，都必须同步设计对应 Qt 表现层。

不采用：

```text
先把所有后端功能补完
↓
最后统一补 Qt
```

采用纵向切片：

```text
Domain / Service / Repository
↓
Persistence
↓
Qt Page / Dialog
↓
Build
↓
Test
↓
Regression
↓
Audit
↓
PASS
```

一个功能包完成完整闭环后，再进入下一个功能包。

---

## 2.3 不无限细化

后续优先处理：

- 核心功能缺失；
- 明显架构问题；
- 数据一致性问题；
- 编译 / 运行问题；
- 可复现性问题；
- 重要 UI / 交互问题；
- 云端化前置问题。

不为了“看起来更复杂”持续增加：

- 无实际需求的类；
- 无实际需求的设计模式；
- 复杂权限编辑器；
- 多余配置中心；
- 大量低价值后台 CRUD；
- 无性能证据的缓存或索引。

---

## 2.4 课程设计尺度下的通用审计标准

本项目后续所有实现、审计与路线裁决统一采用以下尺度：

> **以当前提交版为真实基础做高收益优化，向 Gate 冻结的优秀架构方向靠近，但不以“完整复刻 Gate 1～4”作为目标。**

Gate 文档在当前路线中的作用是：

```text
需求 / 架构方向
+
边界与禁止项
+
发生冲突时的裁决依据
```

而不是：

```text
必须逐条实现的企业级施工清单
```

因此，一个候选改动是否进入正式 IU，优先回答：

1. 是否解决当前代码中的真实 Bug、真实耦合或真实一致性问题；
2. 是否明显提升课程要求中的正确性、面向对象设计、可维护性、可复现性或答辩展示价值；
3. 是否为已经选定的后续高价值功能提供必要前置能力；
4. 是否能在合理工作量内完成完整 build / test / regression / audit 闭环；
5. 是否会引入明显高于当前课程项目收益的复杂度；
6. 如果不做，是否真的阻塞后续路线。

只有前四项收益明确、且第五项成本可接受时，才优先实施。

### Core Architecture Cleanup 阶段的六类优先问题

该阶段曾优先围绕以下六类真实问题审计和选择性实施：

1. Qt → Service 业务边界；
2. ApplicationContext / 统一 MainWindow 的重复职责与生命周期；
3. Diary Public View、作者权威派生与公开荣誉边界；
4. `BUG-RUNTIME-001` 与稳定 Runtime Data Root；
5. 认证 / 密码安全债务；
6. DataManager / DataList 等历史架构债务中真正影响后续开发的部分。

这六类始终只是“优先审计范围”，不是“必须全部做成完整版”的承诺；v1.5 已依据关闭审计将该阶段正式 CLOSED。

### 明确禁止过度工程化

除非当前真实需求、Bug 或已选功能明确需要，否则不主动引入或追求：

- 企业级 DI / Service Locator / ORM / 微服务式拆分；
- 为形式完整而建立大量一对一包装类、接口或 Generic Repository 框架；
- 复杂缓存、多级索引、数据库级优化；
- 不必要的分布式事务、企业级容灾或无限故障注入；
- 以覆盖率数字为目标的大规模测试体系；
- 为追求“理论最纯”而大范围重写已经稳定运行的代码；
- 只因为完整版 / Gate 中存在，就机械增加当前项目并不需要的类、字段、页面或模式。

测试的定位是：

> **为当前重构提供足够的回归安全网，而不是建设企业级 QA 平台。**

架构整理的定位是：

> **解决当前最值得解决的问题，让结构明显变好并为后续精选功能让路，而不是追求架构完美。**

### 审计收口与 reopen 规则

一个 IU 在以下条件满足后应 PASS 并冻结：

- 当前范围目标已经完成；
- build / test / 必要人工回归通过；
- 没有已知阻塞性缺陷；
- 没有违反当前权威边界；
- 继续微调的收益已经明显低于成本。

PASS 后不重复设计。只有出现以下情况才允许 reopen：

- 真实 Bug；
- 已通过功能发生回归；
- 新实现暴露当前权威冲突；
- 新的明确课程 / 业务需求；
- 后续功能证明原冻结点确实成为阻塞。

不得因为“还可以更优雅”“企业项目一般会继续做”而无限 reopen。

### 当前阶段的“足够好”标准

当一个架构切片已经做到：

```text
行为正确
+
职责比提交版明显清楚
+
关键规则不再重复漂移
+
有最小自动化安全网
+
Qt / Console 主要路径可回归
+
后续精选功能不再被它阻塞
```

即可认为达到本课程项目当前阶段的合理完成标准。

不继续为了企业级完整性做低收益扩张。

## 2.5 Qt 为正式产品目标，Console 为兼容目标

从 v1.5 起正式冻结：

```text
Qt
→ 最终课程提交 / 演示 / 功能主线

Console
→ compatibility-only
```

执行规则：

- 新增正式业务功能默认只要求同步 Qt；
- Console 不再要求与 Qt 功能对等；
- 共享 Core 改动若导致 Console 无法编译，只做必要兼容修复；
- 不为了保留旧 Console 交互而限制 Qt / Service 的合理演进；
- Console 继续保留为历史版本、调试入口和版本迭代证据；
- 后续正式人工回归以 Qt 为主，Console 不再要求完整交互回归。

该规则用于降低无收益的双前端维护成本，不改变共享 Core 的正确性要求。

# 6. 核心架构整理 —— CLOSED

Qt UI 2.0 第一轮完成后，本项目进行了显式 Core Architecture Cleanup。

该阶段目标始终是：

```text
Qt Presentation
      ↓
Application / Service
      ↓
Domain + Data Access
      ↓
Persistence
```

但按 §2.4 的课程设计尺度，只处理当前提交版中真实高收益、会造成规则漂移或阻塞后续功能的问题，不追求完整 Gate 复刻。

IU-ARCH-06A 关闭审计结论：

> **CLOSE NOW。**

当前没有发现必须继续留在独立“核心架构整理”阶段解决的阻塞项。

# 10. 云端共享数据库目标

最终联网目标：

> 多台电脑运行同一个 Qt 客户端，并访问同一份云端权威业务数据。

目标效果：

```text
Qt Client A ─┐
Qt Client B ─┼─ HTTPS ─→ Backend API ─→ Cloud Database
Qt Client C ─┘
```

示例：

```text
电脑 A：学生提交志愿记录
↓
云端保存
↓
电脑 B：管理员刷新后立即看到
↓
管理员审核
↓
电脑 A：刷新后看到最新审核结果与积分
```

---

# 11. 云端架构原则

## 11.1 Qt 不直接暴露数据库连接

不建议：

```text
Qt.exe
↓
公网 MySQL / PostgreSQL
```

原因：

- 数据库账号和密码容易暴露在客户端；
- 数据库权限难控制；
- 客户端可以绕过业务规则；
- 后续扩展与安全性差。

采用：

```text
Qt
↓ HTTPS
Backend API
↓
Cloud Database
```

---

## 11.2 保留本地演示能力

最终理想状态：

```text
               ┌── Local Mode
Qt → Service ──┤
               └── Cloud Mode
```

目的：

- 老师离线也能直接运行；
- 云端服务不可用时仍能演示；
- release 包保持可复现；
- 云端模式用于展示多设备共享数据。

---

## 11.3 云端化需要重新进行架构审计

当前历史 Gate 3 的 Repository 设计建立在“只有本地文件后端”的前提上。

一旦真实出现：

```text
Local Persistence
+
Remote Backend
```

存储后端数量已经发生变化。

因此云端化必须显式重新审计：

- Repository 抽象是否需要调整；
- Local / Remote 模式如何切换；
- Service 是否保持不变；
- API 边界；
- 认证方式；
- 并发写入；
- 错误处理；
- 网络不可用；
- 数据同步；
- 本地与云端谁是权威数据源。

不得偷偷用数据库实现覆盖已有架构语义。
