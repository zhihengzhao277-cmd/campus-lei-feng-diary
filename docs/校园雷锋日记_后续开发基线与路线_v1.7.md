## 2.1 课程设计型朴实码风 —— 新的长期实现约束

从 v1.7 起，后续新增代码与现有历史代码都按以下标准审计：

> **代码首先要让本人、老师和后续维护者容易读懂、容易解释、容易调试；不以“看起来高级”作为质量标准。**

统一要求：

- 代码简洁、直接、可读；
- 文件、函数和逻辑分块清晰；
- 命名表达真实业务含义；
- 优先普通循环、条件、STL 容器和清楚的函数调用；
- 一个函数只承担可解释的一组职责，避免无必要的超长函数；
- 也不为了形式漂亮把简单逻辑切成大量过小函数 / 文件；
- 复杂度必须来自真实业务需要，而不是为了展示技巧。

原则上禁止为了“炫技”主动加入：

- 无实际收益的 `constexpr` / `noexcept` 铺满；
- 模板元编程；
- 过度泛型化；
- 一层套一层的 wrapper / helper；
- 为单一调用建立复杂抽象；
- 深层嵌套 lambda；
- 难以答辩解释的语言技巧；
- 只为显得“工程化”而引入的新设计模式。

但这不是对现代 C++ 的机械禁用。

以下已经有真实用途的能力可以继续使用：

- `std::vector`；
- `std::optional`；
- `std::unordered_set`；
- `std::filesystem`；
- `enum class`；
- `std::sort`；
- RAII；
- 其他能够明显解决当前问题、且本人可以解释的标准库能力。

判断标准始终是：

```text
必要
+
清楚
+
可解释
+
收益大于复杂度
```

而不是“语法越新越好”。

---

## 2.2 Qt 代码例外

上述“不要炫技”规则**不要求把正常 Qt 写法改成笨重写法**。

允许继续使用正常 Qt idiom：

- signals / slots；
- `connect(...)`；
- 小型 UI 事件 lambda；
- Qt Model/View；
- Qt Layout；
- Qt Resource；
- 必要的 Qt helper。

Qt 代码的标准仍然是：

> **正常、清楚、符合 Qt 使用习惯。**

不要为了避免 lambda 或 Qt idiom 而把 UI 代码写得更绕。

---

## 2.3 注释规则

注释应解释：

- 这一段为什么存在；
- 当前业务规则；
- 非显然约束；
- 容易误改的持久化 / 状态机 / stable-ID 事实；
- 必要的兼容背景。

不要写大量无信息量注释，例如：

```cpp
i++;  // i 加 1
```

历史源码中的实现过程备注，例如：

```text
AI大修
AI写的
原本 xxx，AI 改成 xxx
临时调试说明
```

不应作为长期源码注释保留。

在一次性代码整理中，应：

- 删除没有代码语义价值的过程备注；
- 或改成真正解释设计意图的注释。

**这不代表隐藏课程要求的 AI 使用情况。**

如果课程要求披露 AI 使用，应在专门的报告 / AI 使用记录 / 课程要求指定位置如实说明，而不是把工具使用过程散落在源码注释中。

---

## 2.4 文件结构规则

项目文件结构继续追求：

```text
一眼能看出模块
+
一个文件有明确职责
+
不过度拆文件
+
不过度堆在一个文件
```

后续新增文件必须有真实职责。

禁止为了“架构看起来复杂”增加：

- 空壳接口；
- 一对一 wrapper；
- 无复用价值的 utility 文件；
- 只有几行转发逻辑的新层。

如果现有文件虽然较长，但结构清楚、功能稳定，也不因文件长度本身强制拆分。

---

## 2.5 历史代码必须进行一次受控整理

本规则不仅约束未来代码。

在 Stable Local Release 最终冻结前，必须安排一次：

```text
Code Readability & Course-Style Audit
↓
Human Audit
↓
Approved Cleanup
↓
build / CTest / regression
↓
PASS / FROZEN
```

目标是检查此前已经实现的：

- `core/`；
- `console/`；
- 关键非业务 Qt 辅助代码；
- 注释与文件组织。

重点处理：

- 明显冗长或难解释的写法；
- 真实存在的过度复杂 helper；
- 无意义的 `constexpr` / `noexcept` 等高级修饰；
- 能用朴实写法等价替代、且不会改变 API / 行为的技巧性代码；
- 过程型 / AI 工具型注释；
- 逻辑分块混乱；
- 重复但可以在不扩大架构的情况下安全收敛的代码。

明确禁止：

- 为“码风统一”重写已经冻结的业务设计；
- 修改状态机语义；
- 修改持久化格式；
- 修改 Service API；
- 修改 Gate 冻结事实；
- 仅因为“还能更优雅”而进行大规模重构。

如果所谓“简化”会改变：

```text
API
行为
持久化
状态语义
架构边界
```

必须 STOP，由人工决定，不允许以 style cleanup 名义偷偷修改。

# 12. Stable Local Release Closure

这是当前进行中的阶段。

目标：

> **把已经通过审计的本地 Qt 产品整理为代码可解释、可提交、可运行、可演示、可复现的稳定版本。**

Stable Local Release 在 v1.7 中明确分三步：

```text
J1. Release / README Refresh
→ 修复当前 stale release、运行依赖、数据文件和 README 真实性

J2. Code Readability & Course-Style Cleanup
→ 对历史代码执行一次受控可读性 / 码风整理
→ 不改变冻结业务和架构

J3. Final Release Refresh + Smoke
→ 基于整理后的最终源码重新生成 release
→ standalone smoke
→ 最终 Git checkpoint / tag 裁决
```

因此，J1 生成的 release 只是本阶段中的当前验证产物；如果 J2 修改了源码，必须在 J3 重新生成最终 release，不能把 J1 的旧二进制当成最终包。

范围：

```text
Git checkpoint
↓
fresh build
↓
CTest
↓
Qt launch / smoke
↓
Runtime data root
↓
source-data safety
↓
Release packaging
↓
README / run instructions
↓
最终本地版本冻结
```

只处理：

- release 阻塞 Bug；
- 构建 / 运行问题；
- 打包问题；
- 路径问题；
- 文档与真实运行不一致；
- 数据污染风险；
- 明显影响最终演示的问题。

明确禁止重新加入新的本地业务功能。

## 12.1 最终运行路径要求

Stable Local Release 必须解决此前每次通过 CMD：

```text
cd <build dir>
set PATH=<Qt>;<MinGW>;%PATH%
leifeng_qt.exe
```

才能启动的问题。

最终用户运行体验必须是：

```text
release/
└── 校园雷锋日记.exe

双击
↓
直接启动 Qt GUI
```

运行发布包时不得要求用户：

- 打开 CMD / PowerShell；
- `cd` 到 build 目录；
- 手动 `set PATH`；
- 依赖开发机 Qt / MinGW PATH；
- 从临时 IU build 目录启动。

开发工具链只允许作为“构建 release”的前置，不允许成为“运行 release”的前置。

## 12.2 Clone 后的可复现要求

GitHub 不提交 `build/` / `release/` 二进制产物时，clone 后不能假设 exe 凭空存在。

正确的最终体验定义为：

```text
git clone
↓
按 README 配好 Qt / MinGW / CMake / Ninja
↓
执行一个明确、可复现的 Release 构建 / 部署入口
↓
生成 release/校园雷锋日记.exe
↓
之后直接双击 exe 运行
```

Stable Local Release 最终冻结前，应提供一个尽量简单的统一入口。

优先考虑：

```text
scripts/build_release.ps1
```

或等价的单一脚本。

该脚本只负责：

- configure；
- build；
- `windeployqt`；
- 拷贝 demo data；
- 生成 `release/`。

它不承担业务逻辑，也不替代 CMake。

是否采用 `.ps1` / `.bat` 由对应 Release IU 结合当前仓库事实裁决，但**不得继续要求用户每次手工输入临时 PATH + build 目录启动命令**。

通过后：

```text
Stable Local Release
→ PASS / FROZEN
```

# 13. Cloud Backend + Shared Database 目标

目标：

> 多台电脑运行同一个 Qt 客户端，并访问同一份云端权威业务数据。

当前只额外记录一个未来方向，不在 v1.7 提前完成详细设计：

- 真实 Cloud Database 数据不提交到 GitHub；
- 生产数据库凭据、API secret、JWT secret、真实 `.env` 不提交到 GitHub；
- GitHub 只允许源码、文档、schema / migration（如后续需要）、`.env.example` 和虚构 / 脱敏 demo 数据；
- Qt 客户端不直接携带公网数据库账号密码；
- 详细的数据保护、认证、云端数据权威与本地/云端切换规则留到 Cloud Architecture Audit 再裁决。

推荐总链：

```text
Qt Client
↓ HTTPS
Backend API
↓
Cloud Database
```

继续禁止：

```text
Qt.exe
↓
公网 MySQL / PostgreSQL
```

同时保留：

```text
Local Mode
```

未来理想方向：

```text
               ┌── Local Mode
Qt → Service ──┤
               └── Cloud Mode
```

# 14. Cloud Architecture Audit —— 必须先做

Cloud 不能直接进入实施。

因为当前架构前提是：

```text
single local persistence backend
```

而 Cloud 会首次真实引入：

```text
Local Persistence
+
Remote Backend
```

必须先审计：

- Local / Cloud 模式选择；
- 权威数据源；
- Service 接口是否保持；
- DataManager / Repository 边界；
- Backend API 粒度；
- 身份认证；
- 凭据处理；
- 并发写入；
- 写冲突；
- 网络失败 / 超时；
- 错误映射；
- 数据同步；
- 模式切换；
- 云端不可用行为；
- 测试与演示方案。

如果真实触发 Gate3 架构冲突：

```text
STOP-14
```

不得偷偷用数据库实现覆盖现有架构语义。
